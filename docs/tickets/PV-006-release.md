## Goal

A researcher can install `paper` 0.1.0 on macOS, Linux or Windows from a GitHub Release with one
command, and the v0.1 acceptance scenario from the roadmap is proven by an automated end-to-end
test. Publishing the release is a separate, maintainer-approved step after this merges.

## Decisions (maintainer and coordinator, 2026-10-17)

- **Channels for v0.1.0 (maintainer):** a GitHub Release with archives for
  `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`,
  `aarch64-unknown-linux-gnu` and `x86_64-pc-windows-msvc`, plus cargo-dist's shell and
  PowerShell installers and checksums. **No** Homebrew tap and **no** crates.io publish yet (later
  tickets: a tap needs its own repo and token; crates.io names are permanent and the binary name
  is still open).
- **Label (maintainer):** the v0.1.0 GitHub Release is a **pre-release**. If cargo-dist can't mark a
  non-suffixed version as a pre-release by config, the release runbook marks it with
  `gh release edit v0.1.0 --prerelease` right after publishing.
- **Version:** `0.1.0` (from `0.1.0-dev`), tag `v0.1.0`.
- **Tooling:** cargo-dist pinned to an exact, recent stable version (at least two weeks old),
  installed for this work **inside the worktree** (`cargo install --locked --root <worktree>/target/tools`),
  never globally. `release.yml` is generated by `dist generate`/`dist init`, not hand-written, and
  the pinned version is recorded in the config so CI regenerates the same file.
- **What runs where:** the release workflow builds on tag push (`v*`) and runs `dist plan` on pull
  requests, so this PR's CI already checks the config. Nothing in this ticket pushes a tag or
  publishes anything.
- **Release notes:** `CHANGELOG.md` with a `## 0.1.0` section that cargo-dist uses as the release body:
  what works (the v0.1 command set), what doesn't yet (undo, lines/tries, milestones, sync, word
  diff), and that it's a walking skeleton for early testers.

## Scope

1. **Acceptance test** `crates/paper-cli/tests/acceptance.rs` running the built `paper` binary in the
   isolated test env (`tests/common/mod.rs`):
   - `paper init` in a folder with `main.tex`, `sections/intro.tex`, `refs.bib` and LaTeX junk
     (`main.aux`, `main.log`): the latex profile is detected and the junk isn't saved.
   - Ten rounds of editing `sections/intro.tex` (and sometimes `main.tex`) and `paper save "…"`.
   - `paper history` lists 11 saves (ten plus "Start project"), newest first; `-n 3` lists three.
   - `paper restore sections/intro.tex --from last~3` puts back the content from three saves ago
     (byte-for-byte), `paper status` shows it as modified, `paper diff` shows the change, then
     `paper save "Restore intro"`.
   - Plain git: `git remote add origin <bare repo>` and `git push -u origin main` succeed; a fresh
     `git clone` of the bare repo has the saved files and `git log` shows the 12 saves; `git
     ls-remote` shows no `refs/paper/*` (I5); `git fsck --strict` is clean in both.
2. **cargo-dist setup:** config for the targets, installers and checksums above; generated
   `release.yml`; `[profile.dist]` as cargo-dist recommends (keep the existing `[profile.release]`).
   `dist plan` succeeds locally and lists exactly the five targets and two installers.
3. **Version** `0.1.0` in `Cargo.toml`, `Cargo.lock` updated, and `paper --version` prints
   `paper 0.1.0`.
4. **Docs:**
   - `README.md`: status says v0.1.0 is a pre-release walking skeleton for early testers (local,
     single line), with an **Install** section (the shell and PowerShell one-liners cargo-dist
     prints, pointing at `lbAntoine/paper-vcs` releases) and the "planned interface" taste marked
     clearly as later versions.
   - `CHANGELOG.md` as decided.
   - `docs/workflow.md` § Releasing: the runbook (bump version, update CHANGELOG, merge, maintainer
     approval, `git tag v0.1.0 && git push origin v0.1.0`, watch the release workflow, mark
     pre-release if needed, smoke-test an installer).
   - `03-architecture.md` § Distribution: what ships now versus later (tap, MSI, crates.io,
     conda-forge in v0.6).
   - `05-roadmap.md` § v0.1: tick the boxes that are done; the acceptance line points to the test.

## Summary

A cargo-dist 0.32.0 release pipeline for v0.1.0 and an automated v0.1 acceptance run. Publishing is a
separate maintainer-approved step (docs/workflow.md § Releasing).

- `crates/paper-cli/tests/acceptance.rs` proves the roadmap's acceptance line with the real binary:
  init a LaTeX paper (profile detected, junk not saved), ten saves, history, restore a file from
  `last~3` byte-for-byte, save, `git push` to a bare repo, then a clone with all 12 saves, paper refs
  present locally but none on the remote, clean `git status` and `fsck`. It passed on the first run
  and on Linux, macOS and Windows CI.
- `dist-workspace.toml` + generated `.github/workflows/v-release.yml`: five targets (macOS Intel and
  ARM, Linux x86_64 and ARM gnu, Windows x86_64), shell and PowerShell installers, checksums, no
  source tarball, no Homebrew/MSI/crates.io. Builds only on tags matching `v**[0-9]+.[0-9]+.[0-9]+*`;
  plan only on pull requests.
- Version 0.1.0; README (pre-release status, install one-liners pinned to v0.1.0), CHANGELOG 0.1.0,
  the release runbook, 03-architecture § Distribution, 05-roadmap § v0.1.

Deviations: the tag trigger is cargo-dist's generated pattern (narrowest with `tag-namespace = "v"`),
not literally `v*`, which renamed the workflow to `v-release.yml`; cargo-dist can't mark 0.1.0 as a
pre-release, so the runbook does it with `gh release edit`; the installers are named after the
`paper-cli` package (revisit with the binary name). Before merge, a temporary commit built all five
targets on this PR (nothing published; Apple Silicon artifact smoke-tested: `paper 0.1.0`, checksum
OK), then was reverted.

Follow-ups (not ticketed yet): a Homebrew tap, crates.io, MSI, musl builds for older Linux clusters,
an install path outside `~/.cargo/bin`, a GitHub tag ruleset (maintainer).
